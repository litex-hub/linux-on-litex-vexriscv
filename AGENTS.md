# AGENTS.md: Linux-on-LiteX-VexRiscv

Linux on a VexRiscv-SMP (RV32) LiteX SoC: `make.py` builds the SoC for ~60 LiteX-Boards targets,
generates the DTS/DTB and the matching Buildroot defconfig; `sim.py` boots the same software
stack (BIOS -> OpenSBI -> Linux -> Buildroot rootfs) in Verilator.

Read the LiteX agent page first: https://github.com/enjoy-digital/litex/wiki/LiteX-for-AI-Agents (framework map, conventions, how to
verify a change, contribute back). Index of the whole wiki for agents: https://github.com/enjoy-digital/litex/wiki/llms.txt.

## Where things are

- `make.py`: CLI (`--board`, `--build`, `--load`, `--flash`, `--rootfs`, VexRiscv-SMP options such
  as `--cpu-count`, `--with-fpu`), board capabilities -> SoC kwargs, Buildroot defconfig generation.
  `./make.py --help` lists the boards.
- `boards.py`: one `Board` subclass per board (LiteX-Boards target + `soc_capabilities`); the board
  name is the class name in snake case (`ArtyA7` -> `arty_a7`).
- `soc_linux.py`: `SoCLinux` wrapper (extra peripherals, DTS generation/compilation, DTB overlays).
- `sim.py`: Verilator simulation (VexRiscv-SMP + SDRAM model, RAM preloaded from `images/boot_ram0.json`).
- `images/`: `boot_<rootfs>.json` (load addresses for `Image`, `rv32.dtb`, `rootfs.cpio(.gz)`,
  `opensbi.bin`); the binaries come from the prebuilt archive or Buildroot, not from git.
- `buildroot/`: `BR2_EXTERNAL` tree (`configs/litex_vexriscv_defconfig`, kernel configs, overlays, packages).
- `test/`: `test_build.py` (per-board generation, CPU variants, defconfigs), `test_jtag_debug.py`.
- `HOWTO.md`: using the peripherals from Linux.

## Verify a change

```sh
python3 -m unittest test.test_build.TestBuild.test_buildroot_defconfigs test.test_jtag_debug   # < 1 s
./make.py --board=arty --cpu-count=1                    # SoC + BIOS + DTB, no bitstream (~15 s)
LLV_BOARD=arty python3 -m unittest test.test_build.TestBuild.test_boards   # what each CI shard runs
python3 -m unittest -v test.test_build.TestBuild.test_cpu_count test.test_build.TestBuild.test_cpu_variants
timeout 1800 ./sim.py < /dev/null                      # Linux in Verilator, needs the images below
```

- Without `--build`, `make.py` elaborates the SoC, compiles the BIOS and generates
  `build/<board>/` (`csr.csv`, `csr.json`, `<board>.dts`, gateware Verilog, `buildroot_defconfig`) and
  `images/rv32.dtb`: enough to check a change without the FPGA toolchain. `--build` needs the vendor
  toolchain (Vivado, Yosys/nextpnr, Quartus, Efinity...).
- Changing a board or a capability: run its `LLV_BOARD=<board>` test; changing `make.py`/`soc_linux.py`
  logic shared by all boards: also the CPU tests and a few boards from different vendors (CI builds
  every board in `boards.py` except those excluded in `test/test_build.py`).
- Non-default VexRiscv-SMP configurations (cache sizes, AES, FPU...) are generated by SpinalHDL on
  first use and need `sbt`; the default ones are pregenerated.
- A RISC-V GCC (`riscv64-unknown-elf-`, `riscv-none-elf-`...) and `dtc` are needed for the BIOS and DTB.
- An import proves nothing; elaboration proves the Python and the Verilog generation; timing and Linux
  boot need a build and a board (or `sim.py`). Say in the PR what ran where.

## Pitfalls

- `make.py` writes `images/boot.json` and `images/rv32.dtb` (not ignored by git): do not commit them.
  The tests `rm -rf build/`.
- The DTB must match the bitstream (CSR map, RAM size, rootfs mode): after changing options, use the
  `images/rv32.dtb` generated by the same `make.py` command, not one from another archive.
- `--rootfs=nfs` needs a board with the `ethernet` capability and a matching Buildroot defconfig
  (`build/<board>/buildroot_defconfig`); the same goes for USB host, AES and FPU options.
- `sim.py` needs `images/Image`, `images/opensbi.bin` and `images/rootfs.cpio.gz` (from the prebuilt
  `linux_*.zip` of issue #164, gzip its `rootfs.cpio`, or from Buildroot). It is slow (~20 min from
  start to the `buildroot login:` prompt on a desktop) and interactive (console on stdin/stdout): run
  it with a timeout and stdin redirected when scripted, and check the log for `Liftoff!`,
  `OpenSBI`, `Linux version` and `login:`.
- `--with-cpu-jtag-debug` requires `--with-privileged-debug`, is Xilinx-only, and cannot be combined
  with `--jtag-tap`.

## Rules

- Style: https://github.com/enjoy-digital/litex/blob/master/doc/coding_style.md (match the
  surrounding file; `module: Description of the change.` commit titles; one change per commit).
- Never edit generated files (`build/`, `csr.h`, `csr.csv`, the Verilog, the DTS/DTB): change the Python.
- Board support comes from LiteX-Boards: fix board issues there, keep `boards.py` to capabilities
  and project-specific settings.
- One topic per pull request, from `master`, with what was tested and on which hardware; say
  that an agent wrote it and who supervised. Do not rename options or reformat unrelated code.
- Hardware: never flash a board or write its SPI flash (`--flash`) unless the user asked; `--load`
  (volatile) is the default for experiments.

## Debug on hardware

Load the Linux images with `litex_term --images=images/boot.json /dev/ttyUSBX` (serial, works on all
boards), TFTP or SDCard (see the README). Method: https://github.com/enjoy-digital/litex/wiki/Debug-A-SoC-On-Hardware (check the link and `--ident` first,
registers before traces, narrow LiteScope captures). `litex_mcp` gives the same loop as MCP tools
(CSRs by name, LiteScope captures, builds with parsed timing, simulation): https://github.com/enjoy-digital/litex/wiki/LiteX-for-AI-Agents#drive-a-soc-through-mcp.
CPU debug over JTAG/GDB: https://github.com/enjoy-digital/litex/wiki/JTAG-GDB-Debugging-with-VexRiscv-SMP-NaxRiscv-VexiiRiscv-CPUs.
